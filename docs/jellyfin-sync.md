# Jellyfin viewing sync

The service can compare what was played in Jellyfin with the tracking. The structure (seasons, episodes, provider ids) comes from the Jellyfin API and the dates from Jellystat's `jf_playback_activity` table, read directly from its Postgres database in a read-only session. Jellyfin 12 only accepts the `Authorization: MediaBrowser Token="..."` header, which is what the client sends. Jellystat only records real playback, so items marked as watched by hand never show up. Syncing is off unless the four required variables are set, and then runs for each user with a Jellyfin account in their settings (`jellyfinUser`, see [Per-user settings](users.md#per-user-settings)); a user without one is never synced, so nobody's viewings are read for them.

| Variable                                     | Default                   | Meaning                                             |
| -------------------------------------------- | ------------------------- | --------------------------------------------------- |
| `JELLYFIN_URL`, `JELLYFIN_TOKEN`             | required                  | Jellyfin address and an API key                     |
| `JELLYSTAT_DB_HOST`, `JELLYSTAT_DB_PASSWORD` | required                  | Jellystat Postgres host and password                |
| `JELLYSTAT_DB_PORT`, `_USER`, `_NAME`        | 5432, postgres, jellystat | Rest of the connection                              |
| `SYNC_TIME_ZONE`                             | `Europe/Madrid`           | Time zone that decides on which day a viewing falls |
| `SYNC_WEBHOOK_DELAY_SECONDS`                 | 120                       | Quiet time after a webhook before the sync runs     |
| `SYNC_WEBHOOK_SECRET`                        | unset                     | Secret the webhook must send (16+ characters)       |

Rules: an item counts as watched when 90% of its runtime was played in one day, or, when playback never reaches that because intros and credits were skipped, when Jellyfin marks it as played for the tracked account (the day with the most playback is used). A watched movie without a finish date completes with that day, and later viewings become rewatches (a viewing the day after the recorded date is taken as the same one). Each watched day of an episode is stored as one viewing that starts and ends that day, merged with what the user marked in the web app (nothing is ever removed). With `TMDB_API_KEY`, a series linked to TMDB is synced by episode id: each watched episode is matched to its TMDB episode through its TheTVDB id (`/find`, remembered in `tvdb-episode-ids.json` in the data directory, where a miss is asked again after 7 days) or, when it has none, through its air date if exactly one episode of the series' TMDB ordering aired that day; before all that, the TMDB id Jellyfin itself gives the episode wins when the ordering has it, and an episode still unmatched at the end is matched by position (its index in the season when the Jellyfin season has as many episodes as the ordering's season of the same number, else its absolute position when all numbered seasons have as many episodes as the ordering has aired), never over an episode matched by id, and recorded under that TMDB id in the season of the ordering that holds it (the series' episode group, or the regular seasons); the seasons of the ordering the series lacks are created, whatever numbering Jellyfin uses. Episodes that cannot be matched are reported as the `episode_unmatched` warning and listed in the web app, with links to TMDB, on the series and season pages. A dated viewing from the sync replaces the unknown-date first viewing of an episode (a season completed by hand) unless it is after the season's finish, in which case it is a rewatch. Without a TMDB id or key, or when TMDB cannot be read, episodes are stored by the library's numbering. The season follows its episodes, the same way as when they are marked by hand: the first watched episode puts the season in progress; once every episode of the season is watched and none is still to air it completes; a play after the season's finish is a further viewing of its episode, and the season is computed again from the episodes' viewings as the web app does: a complete later pass is a closed rewatch, and an incomplete one is a season rewatch only while the user has asked to watch the season again, which the sync never sets. The season's `started_at` is the earliest start among its episodes' first viewings and `finished_at` the latest finish among them once every aired episode is watched; seasons without dated episode viewings keep their dates. Ratings, reviews and notes are never touched. Every movie viewing the sync records (a first viewing or a rewatch) and every season it completes is marked as pending review: the title is published, but the site feeds leave it out until it is confirmed in the web app (Save and confirm), so a feed entry never goes out before the rating and review are written. Library seasons are paired with stored seasons by Jellyfin id, a season override, the date of the first episode (never the number, so TMDB season 3 pairs with Jellyfin season 4 for Lupin) and finally the number for stored seasons that have no air date. Series are paired with stored ones by TheTVDB id, then TMDB id; when Jellyfin only has the TheTVDB id and `TMDB_API_KEY` is set, the TMDB id is looked up first, so a series added from TMDB is not created twice. Movies and series the sync creates get their TMDB metadata and artwork right after the write (a failed refresh leaves them as created). Titles without any id go to the unlinked inbox. Playback of items that left the library or came back under new ids cannot be matched and is only counted.

To sync without clicking, point the Jellyfin Webhook plugin at `POST /api/sync/webhook`. The body is ignored: every request queues one sync for each user with a Jellyfin account after `SYNC_WEBHOOK_DELAY_SECONDS` of quiet (so Jellystat has recorded the playback), a burst of events is one run, an event during a run triggers another afterwards, and failures retry with backoff and alert through ntfy. What the sync writes is published and mirrored like any other edit. In the plugin add a Generic destination with that URL, a JSON body such as `{"event": "{{NotificationType}}"}`, the `Content-Type: application/json` header, the notification types Playback Stop and User Data Saved, and your user as the only user filter. Set `SYNC_WEBHOOK_SECRET` (for example `openssl rand -hex 32`) once metrack is reachable from outside the local network: requests without it answer 401. Send it in an `X-Webhook-Secret` header (another header in the same Generic destination), or, for a sender that cannot set headers, as `?token=<secret>` in the URL (masked in metrack's logs, but a URL can end up in other logs, so prefer the header).

On a Cloudflare Worker, syncing is done by the home connector instead (see [connector.md](connector.md)); the web sync page there only says so.

The first pass is report only:

```sh
node --disable-warning=ExperimentalWarning apps/server/dist/cli.js sync --verbose
curl http://localhost:8097/api/sync/report
```

`sync` (as user 1, or `--user <id>`) without `--apply` opens the database read-only. `sync --apply` and `POST /api/sync/apply` with `{ "confirm": true }` recompute the plan for the signed-in user and write it in one transaction. The settings page has the same two steps.
