# HTTP API

The private editing API served by `apps/server` under `/api`. Every route needs a signed-in session or a personal API token except the ones marked public below (see the security model in [users.md](users.md)). Requests and responses are JSON unless noted. Every type named here is exported from `@metrack/domain` (`packages/domain/src/api` and the entity types next to it), so the web app imports the contract instead of redefining it.

## Conventions

- Dates are ISO `YYYY-MM-DD` and must be real calendar dates. Ratings are numbers from 0 to 10.
- Bodies are validated against a schema. Unknown fields are rejected, not ignored.
- Errors always have the shape `ApiErrorBody`: `{ "error": "message for people", "code": "stable_code", "details": optional }`. Status codes: 400 validation or bad input, 401 no session (`unauthenticated`) or a bad token (`bad_token`), 403 an instance-wide action for the owner only (`owner_only`), a route that needs the browser session (`session_required`) or a write with a read-only token (`read_only_token`) or adding by hand or using own artwork as a normal user (`trusted_only`), 404 unknown record, 409 conflict with the current state, 413 a body or image over the size limit, 501 a provider or source that is not configured, 502 a provider failed.
- Common codes: `unauthenticated`, `bad_token`, `owner_only`, `session_required`, `read_only_token`, `trusted_only`, `owner_role_fixed`, `catalog_shared`, `validation_error`, `not_found`, `conflict` (a unique id is taken), `invalid_reference`, `invalid_date`, `invalid_dates`, `invalid_transition`, `invalid_rewatch`, `already_added`, `provider_not_configured`, `no_metadata_source`, `provider_error`, `provider_not_found`, `sync_not_configured`, `unsupported_image_kind`, `url_not_allowed`, `image_download_failed`, `unsupported_image`, `image_not_found`, `image_too_large`, `image_quota_exceeded`, `body_too_large`, `ids_required`, `invalid_ids`, `cannot_resolve`.
- Any successful write under `/api` queues a refresh of the vault mirror of each user who has one, after a short debounce. Reads never do.
- On the Worker, any successful `POST`, `PUT`, `PATCH` or `DELETE` under `/api` by a signed-in user also bumps that user's content version (`user.content_version`), which invalidates the stored renders of their public pages. See `docs/worker.md`.
- `cover` and `banner` hold either the URL of a linked provider image (TMDB, Steam or IGDB, see `isLinkedImageUrl`) or `/api/images/<hash>`, a copy in the server image store. Clients paint linked images at the size they need with `sizedImageUrl`.

## Sessions

A session is an `HttpOnly`, `SameSite=Lax` cookie named `metrack_session` that lasts 30 days (`Secure` when served over HTTPS). The server stores only the SHA-256 of its token. Public routes: `GET /api/health`, `GET /api/invites/{code}`, `POST /api/sync/webhook`, `POST /api/auth/logout`, `POST /api/auth/token-login`, the Google sign-in routes (when configured) and the dev login routes.

- `GET /api/auth/me`: the signed-in `User` (`{ id, name, email }`).
- `POST /api/auth/token-login` (`TokenLoginRequest`, `{ "token": "mt_..." }`, answers the `User` and sets the session cookie): exchanges a personal API token for a normal session of the token's user, with the same cookie, flags and 30-day lifetime as any other session. Only a `write` token may do it: a `read` token answers 403 `read_only_token`. An unknown, malformed, revoked or expired token answers 401 `bad_token`. The route is public and judges only the body, never an `Authorization` header, and the secret is looked up by its SHA-256 like everywhere else and never logged. It is always available (home server and Worker), has no rate limit, and is what the web login screen's "Sign in with an access token" form calls.
- `POST /api/auth/logout`: ends the session and clears the cookie, 204 (also without a session).
- Everything else answers for the signed-in user only. An id that belongs to someone else is a 404, as if it did not exist. Titles are a shared catalog plus a personal entry: adding a title that another user already has reuses the same id, and changing a catalog field that is not a hand edit (an external id, a season number) of a title someone else also has answers 409 `catalog_shared` with the fields in `details.fields`.
- Only user 1, the owner, may call the instance-wide routes: `GET` and `POST /api/backups`, `POST /api/images/cleanup` and `DELETE /api/images/:hash`. Others get 403 `owner_only`. Sync acts on the signed-in user, with the Jellyfin account in their settings.
- Every `User` has a `role` (`UserRole`): user 1 is always the `owner`; the owner makes others `trusted` or `normal` (the default). Only the owner and trusted users may add items by hand, `POST /api/{collection}` (`canAddByHand`); normal users add titles from the providers with `POST /api/titles` and get 403 `trusted_only` there. An item added by hand has no provider id, belongs to whoever created it and is never shared; it stops belonging to anyone once it gets a provider id, since it is then that title's catalog row.
- `GET /api/auth/google/start` and `GET /api/auth/google/callback`: only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set, otherwise they answer 404 (and `GET /api/health` reports `features.googleLogin: false`). `start` redirects (302) to Google's authorization endpoint with `scope=openid email profile`, a random `state` and `nonce` and a PKCE S256 challenge, and keeps their secrets, and the invitation code of `?invite=<code>` when it is given and made of URL-safe characters, in the `metrack_google_flow` cookie (10 minutes, `HttpOnly`, `SameSite=Lax`, `Path=/api/auth/google`). The redirect URI is `<request origin>/api/auth/google/callback`. `callback` checks the `state` against that cookie, exchanges the code at Google's token endpoint and checks the id token's `iss`, `aud`, `exp` and `nonce` (its signature is not checked: it comes straight from Google over TLS). A Google account signs in as an existing user when its `sub` is already stored on a user, or when the token's email is verified and equal (ignoring case) to the email of a user that has no `sub` yet, in which case the `sub` is stored; neither spends an invitation use. Otherwise, if the email is verified and the cookie carries an invitation that is not expired, revoked or used up, it creates a `normal` user with the Google name (or the part of the email before the `@`), the verified email and the `sub`, spends one use of the invitation and records it, all in one atomic step (see Invitations), and signs them in with `needsWelcome` true. Without a usable invitation no user is ever created. On success it sets the normal session cookie and redirects to `/`; otherwise it redirects to `/invite/<code>` (the invitation could not be used, so nothing was created), to `/login?error=google_no_account` (no matching user and no invitation) or `/login?error=google_failed` (anything else, with the reason logged without codes or tokens).
- `GET /api/auth/dev-users` and `POST /api/auth/dev-login` (`DevLoginRequest`, `{ "userId": 2 }`, answers the `User` and sets the cookie): only with `DEV_LOGIN=true`, otherwise they answer 404. They let anyone who reaches the server sign in as any user with no password, for development and a trusted local network.

## Invitations

An invitation is a link `https://<host>/invite/<code>`. The code is 32 random bytes in base64url and only its SHA-256 is stored, so it is answered once, when the invitation is created. An invitation has a number of uses (1 to `INVITE_LIMITS.maxUses`, 100), an expiry (1 to 90 days, 7 by default) and can be revoked while it has uses left. Its `status` is `valid`, `expired`, `revoked` (wins over the others), `used_up` or `unknown` (only in the preview). Each use is stored in `invite_use` with the user it created.

- `GET /api/invites/{code}` (public, spends nothing): `InvitePreview`, `{ status, inviter }`, where `inviter` is the owner's display name. An unknown code answers 200 with `status: "unknown"`. The invitation page of the web app reads it, and offers "Sign in with Google" (`/api/auth/google/start?invite=<code>`) only for a valid one.
- `GET /api/invites` (owner only): `Invite[]`, newest first: `{ id, maxUses, uses, createdAt, expiresAt, revokedAt, status, usedBy: [{ userId, userName, usedAt }] }`; `userId` and `userName` are null once that account is erased.
- `POST /api/invites` (owner only, `CreateInviteRequest`: `{ maxUses, expiresInDays? }`): answers 201 `CreatedInvite`, `{ invite, code }`. 400 for values out of range.
- `DELETE /api/invites/{id}` (owner only): revokes an invitation, 204; 409 `invite_not_revocable` when it does not exist, is already revoked or has no uses left.

The use is spent atomically with the creation of the user. On SQLite (in a transaction) and on D1 (in one `batch`, the only atomicity D1 offers) three statements run in order: an `UPDATE invite SET uses = uses + 1` guarded by `revoked_at IS NULL AND expires_at > now AND uses < max_uses`, an `INSERT INTO user ... SELECT ... WHERE changes() > 0` and an `INSERT INTO invite_use ... SELECT ... WHERE changes() > 0`, so the user and the use record exist only if the guarded update took the use. Two people racing for the last use create exactly one user. Both owner-only routes refuse API tokens.

## First entry

A user created through an invitation has `onboarded_at` null until they confirm their name and handle; `GET /api/account` answers `needsWelcome: true` for them and the web app shows the first-entry form until they do. Users created any other way, and every user from before the migration, are already welcomed.

- `POST /api/account/welcome` (browser session only, `WelcomeRequest`: `{ name, handle }`): stores the display name (1 to 80 characters after trimming, 400 `invalid_name`) and the public page handle, which is validated and normalized exactly as in `PATCH /api/settings/public-page` (400 `invalid_handle`, 400 `handle_required` when empty, 409 `handle_taken`), leaves the page switched off, marks the user as welcomed and answers the updated `User`. 409 `already_welcomed` when they already confirmed.

## Personal API tokens

Programs (a sync connector, the Obsidian plugin) call the API on a user's behalf with a token in `Authorization: Bearer <secret>` instead of the session cookie. A request with an `Authorization` header is judged by its token alone: an unknown, malformed, revoked or expired one answers 401 `bad_token` even next to a valid cookie. The server stores only the SHA-256 of each secret, which starts with `mt_`.

- Scopes (`TokenScope`, `TOKEN_SCOPES`): `read` may only `GET`, anything else answers 403 `read_only_token`; `write` may also change the user's library.
- `connector` (only the owner can create one, else 403 `owner_only`) is accepted on `/api/connector/*` and nowhere else: any other route answers 403 `connector_token_only`. See [connector.md](connector.md).
- A token never reaches the owner-only routes (even the owner's own token), the settings or token routes: they answer 403 `session_required`.
- Last use is recorded at most once a minute. Deleting a user deletes their tokens.

Managing tokens needs the browser session:

- `GET /api/tokens`: the signed-in user's tokens as `ApiToken[]` (`{ id, name, scope, createdAt, expiresAt, lastUsedAt }`), newest first. The secret is never listed.
- `POST /api/tokens` (`CreateTokenRequest`: `{ name, scope, expiresInDays }`): `name` is 1 to `TOKEN_NAME_MAX` (60) characters after trimming (`invalid_token_name`), `expiresInDays` one of `TOKEN_LIFETIMES_DAYS` (30, 90, 365, or `null` for never; `invalid_token_lifetime`). Answers 201 `CreatedToken` (`{ token, secret }`); the secret is shown only here.
- `DELETE /api/tokens/{id}`: revokes one of the user's tokens, 204; 404 when they have no token with that id.

```sh
curl -H "Authorization: Bearer mt_..." http://localhost:8097/api/media
```

## Collections

`COLLECTIONS` lists the URL segments: `movies`, `series`, `seasons`, `games` and `books`. They map to the entity types `Movie`, `Series`, `Season`, `Videogame` and `Book` (`MEDIA_TYPE_OF_COLLECTION` gives the `MediaType`). Series have no tracking of their own: status, dates, rating and rewatches belong to their seasons, and the series only has a free-text `review`.

### Listing: `GET /api/media`

One list across every collection, as `MediaPage` (`{ items: MediaSummary[], total }`). Query parameters (`MediaQuery`):

- `type`: `movie`, `series`, `season`, `videogame` or `book`.
- `status`: one of `MEDIA_STATUSES`. A series matches when any of its seasons has that status.
- `q`: text search over the title and original title (and the series title for seasons), ignoring case and accents.
- `sort`: `title` (default), `recent`, `rating`, `startedAt`, `finishedAt`, `releaseDate` or `id`. `order`: `asc` (default) or `desc`. Rows missing the sort value always come last. `recent` puts titles in progress first and then orders by the latest day each was started, finished or rewatched, newest first unless `order=asc`; a series takes both from its seasons. The web library uses `recent` by default.
- `limit` (1 to 1000, default 50) and `offset`.

A `MediaSummary` has `type`, `id`, `title`, `subtitle`, `releaseDate`, `cover`, `banner`, `status`, `rating`, `startedAt`, `finishedAt`, plus `seriesId` and `seriesTitle` for seasons and `seasonCount` for series, and `pendingReview` (a series is pending when any of its seasons is). A season without its own cover or banner shows the one of its series; books have no banner.

### Per collection

- `GET /api/{collection}/{id}`: the entity as `MediaDetail<T>`, which adds `editedFields` (fields a refresh will not overwrite) and `fetchedAt`. A series answers `SeriesDetail`: it also carries `seasons` (ordered by number).
- `POST /api/{collection}`: creates an entity and answers 201 with its detail. The body is `CreateInput`: any entity field except `id`, `cover` and `banner`. `title` is required. Status defaults to `planned`. There is no collection route for seasons: a season is never created by hand, it comes from the series' TMDB ordering (a refresh, switching the ordering, the release watcher) or from the Jellyfin sync, and `POST /api/seasons` answers 404.
- `PATCH /api/{collection}/{id}`: edits any subset of the fields (`EditablePatch`) and answers the new detail. At least one field is required. See the rules below.
- `DELETE /api/{collection}/{id}`: 204. Deleting a series deletes its seasons. Image files stay in the store until `POST /api/images/cleanup`.
- `DELETE /api/{collection}/{id}/edited/{field}`: stops protecting a hand-edited field, so the next refresh may overwrite it. 404 if the field is not marked.

Editable fields per collection:

- `movies`: `tmdbId`, `jellyfinId`, `title`, `originalTitle`, `releaseDate`, `overview`, `genres`, `cast`, `director`, `follow`, `note`, `slug`, `tags` and the tracking fields.
- `series`: `tmdbId`, `tvdbId`, `jellyfinId`, `title`, `originalTitle`, `firstAirDate`, `overview`, `genres`, `cast`, `follow`, `note`, `review`, `slug`, `tags`.
- `seasons`: `number`, `tmdbSeasonNumber`, `jellyfinId`, `title`, `overview`, `firstAirDate`, `episodeCount`, `slug`, `tags` and the tracking fields.
- `games`: `igdbId`, `steamAppId`, `steamGridDbId`, `title`, `releaseDate`, `overview`, `genres`, `developer`, `platforms`, `note`, `timeSpentMinutes`, `slug`, `tags` and the tracking fields.
- `books`: `openLibraryId`, `isbn`, `title`, `authors`, `publisher`, `pageCount`, `releaseDate`, `overview`, `genres`, `note`, `timeSpentMinutes`, `slug`, `tags` and the tracking fields.

The tracking fields are `status`, `startedAt`, `finishedAt`, `rating`, `review`, `rewatches` and `pendingReview`. `pendingReview` is set by the Jellyfin sync on every viewing it records and cleared by patching it to `false`; while it is set, the exported page carries `pending_review: true` and the site feeds leave it out.

### Time spent

`timeSpentMinutes` on games and books is the time the user has spent on the item, in whole minutes: an integer from 0 to 6000000 (100000 hours) or `null` for no data, which is not the same as 0. The web app asks for hours (`12.5` or `12:30`) and sends minutes. Games and books without it do not count in the statistics, which say how many finished ones are missing.

Movies and series have no field of their own: their time is computed when read. A movie counts its `runtime` (minutes, from TMDB `/movie/{id}`, filled in when the movie is created or refreshed and by a background backfill of the movies stored before it existed; `0` means TMDB has none) once for the first viewing of a completed movie and once for each finished rewatch, and counts nothing without a running time. A season counts the `runtime` of every viewing of every watched episode in `series_episode_entry`, rewatches included and skipped episodes left out; an episode without a running time takes the season's average, then the series' `episodeRuntime` (TMDB `episode_run_time`), and counts for nothing when there is neither. A season without an episode catalog counts its watched episodes at the series' `episodeRuntime`. `GET /api/series/{id}` and `GET /api/seasons/{id}` carry the result as `timeSpentMinutes` (`null` when there is no data); `runtime` and `episodeRuntime` are read-only catalog fields.

### Editing rules

- `status` follows the domain transition rules (`canTransition`). A forbidden move answers 409 `invalid_transition` and changes nothing. Entering `in_progress` sets `startedAt` when empty and keeps `finishedAt`; entering `completed` sets `startedAt` when empty and `finishedAt` to today, unless the item was already finished, in which case `finishedAt` keeps the first finish. Leaving `completed` for `in_progress` opens a viewing `{ startedAt: today, finishedAt: null }` in `rewatches`; completing again closes it with today (on the finish day itself it is dropped instead), and without an open viewing a later day is added as a viewing without a start. Pausing keeps the open viewing, planning or dropping discards it. Dates sent in the same request win over those automatic dates, and a request that sends `finishedAt` without `startedAt` leaves an empty start date empty instead of filling it with today. Sending the current status changes nothing.
- `finishedAt` before `startedAt` answers 400 `invalid_dates`.
- `rewatches` is a list of viewings `{ "startedAt": "YYYY-MM-DD" | null, "finishedAt": "YYYY-MM-DD" | null }`, the viewings after the first (the first lives in `startedAt` and `finishedAt`). Sent in a patch it replaces the whole list, and each item may also be a plain date string (a closed viewing without a start). The server normalizes it: closed viewings sorted by finish then start, duplicates removed, at most one open viewing (no finish), always last. Responses always carry objects. Prefer the two routes below to add or remove one.
- Metadata fields are marked as hand-edited when a patch actually changes them: `title`, `originalTitle`, `releaseDate`, `firstAirDate`, `overview`, `genres`, `cast`, `director` (movies and series), `developer`, `platforms` (games), `authors`, `publisher`, `pageCount` (books), `episodeCount` (seasons). Sending a form with unchanged values does not mark anything. Ids, tracking, `note`, `tags`, `slug` and `follow` are never marked. Choosing or removing an image marks `cover` or `banner`.
- Every title is stored as a catalog row (what providers describe: ids, metadata, default cover and banner) plus a personal entry (tracking, `note`, `tags`, `slug`, `follow`, `jellyfinId`, review). A hand edit of a metadata field or an image is kept in the entry and shown over the catalog; a refresh only updates the catalog, and `DELETE .../edited/{field}` drops the hand edit so the catalog value shows again.

### Rewatches (not for series)

- `POST /api/{collection}/{id}/rewatches` with `{ "date": "YYYY-MM-DD" }` or `{ "startedAt"?: "YYYY-MM-DD" | null, "finishedAt": "YYYY-MM-DD" }` (`RewatchRequest`): adds a closed viewing. Only completed items can be rewatched, otherwise 409 `invalid_rewatch`. Answers 201 with the detail.
- `DELETE /api/{collection}/{id}/rewatches/{date}`: removes the closed viewing that finished on that date, 404 if there is none.

### Season episodes

- `GET /api/seasons/{id}/episodes`: the episodes of a season the user has an entry for (404 otherwise) and what the user watched of them: `{ seasonId, source, fetchedAt, complete, episodeCount, watchedCount, datesDerived, episodes: [{ key, number, tmdbId, title, airDate, runtime, overview, stillPath, watched, skipped, viewings, filler }] }`. `filler` is the AnimeFillerList category of the episode (`filler`, `mixed`, `mangaCanon` or `animeCanon`) once the filler preview has been opened for the series, `null` before; it is read from the shared `season_filler` row of the season, with no external request. An episode is identified by its TMDB episode id: `key` is that id as a string, or `s<season>e<episode>` (metrack's numbering of the season) when the episode has no id. The user's watches are one row per series, `{ "<key>": Viewing[] }`, so switching the series to another episode group moves no watch, only the seasons that show it. `viewings` use the same `{ startedAt, finishedAt }` shape as rewatches; a watched episode with an empty list was watched on an unknown date. A completed season whose `watchedCount` is above zero and has no watched episode of its own counts as every episode watched, without dates. `stillPath` is a TMDB image path to load from `image.tmdb.org`. The catalog is shared by all users, one row per season, in the series' ordering. It is read with the user's watches of the series (two rows by primary key); when it is missing, stale (after one day while the season is airing, after 30 days otherwise) or incomplete, and the series has a TMDB id, TMDB is asked: one request for the season of the series' episode group, or one for a regular season. A regular season over 1 MB (declared or read) is filled in by chunks instead: 15 single-episode requests per call, the partial catalog is stored and `complete` is `false` until a later call has fetched every episode up to the season's `episode_count`; the client asks again while `complete` is `false`. When a catalog that was complete goes stale and is over 1 MB, the chunks are kept apart (`refill`) and the old complete catalog is served, with `complete` true, until the new one is complete. A complete catalog sets the season's `episode_count` to its length, which bumps the signed-in user's content version when it changes so the library list revalidates. An error, a series without a TMDB id or no TMDB client leave the season with `source: "numbers"`, `fetchedAt: null` and episodes that only have their numbers (or what a partial catalog already holds), and nothing is stored, so the next visit tries again. When the catalog has TMDB ids, the user's watches of the season stored under `s<season>e<episode>` keys move to the ids of the same numbers. The library list and the public pages never read episodes: they only use `watchedCount` and `episodeCount` of the season itself.
- `PATCH /api/seasons/{id}/episodes` (write scope): changes the user's watched episodes of the series with one operation on keys of this season's episodes: `{ "op": "mark", "keys": ["6701926"], "date": "2026-03-01" }` adds a viewing `{ startedAt: date, finishedAt: date }` to each episode (a `null` date marks them watched on an unknown date, an empty list, and adds nothing to an episode that is already watched; a viewing with the same finish date as an existing one is not added twice), `{ "op": "unmark", "keys": [...] }` takes away the last viewing of each episode (the episode itself when it has one or none), and `{ "op": "setViewings", "key": "6701926", "viewings": [{ "startedAt": "2026-03-01", "finishedAt": "2026-03-01" }] }` replaces the viewings of one episode (every viewing needs a `finishedAt` that is not before its `startedAt`; an empty list keeps the episode watched on an unknown date). `{ "op": "skip", "keys": [...] }` marks episodes skipped (not watched, and not owed for the season to complete; an episode whose only watch is on an unknown date loses that watch, one with a dated viewing is refused with 400 `episode_has_viewings`) and `{ "op": "unskip", "keys": [...] }` forgets the skip; watching a skipped episode (`mark`, `setViewings`, or a Jellyfin play) unskips it. The season is complete when every aired episode is watched or skipped, and its finish date comes from the watched ones; `skippedCount` and each episode's `skipped` come with every answer, and `season_entry.skipped_count` is kept in the same atomic write. A key must be one `GET` lists for the season, otherwise 400 `episode_out_of_range`. A completed season whose `watchedCount` is above zero and records none of its episodes counts as every episode watched on an unknown date, so the first change writes those episodes first. After any change the user's entries of every season of the series whose complete catalog is known are computed again from scratch from the series' watches, in the same atomic write as the watches: `watchedCount`, `skippedCount`, status, dates, rewatches and the intention to watch again (`wantsRewatch`); nothing is patched, so unmarking what was marked leaves the season as it was. Pass N of a season is the N-th viewing of each of its episodes. The first pass is complete when every episode that is not skipped has aired and has a viewing, and the season is then `completed` (otherwise `in_progress`, a planned or paused season included); its `startedAt` is the earliest start among the first viewings when every one has a start and its `finishedAt` the latest finish among them when every first viewing has one, and the stored dates stay where the viewings have none (a start after the finish is brought back to it, and an unfinished first pass whose viewings are all dated has no finish). A later pass is complete when every aired episode that is not skipped has that many viewings, and each complete later pass is a closed rewatch from its earliest start to its latest finish. An incomplete later pass with a dated viewing is an open rewatch only while `wantsRewatch` is true, which `PUT /api/seasons/{id}/rewatch-intent` sets or clears and which clears itself when a rewatch completes; without it, watching an episode again only adds a viewing to that episode. A completed season that records none of its episodes counts as every episode watched on an unknown date first, so a mark on it is the second pass. Dropped seasons and seasons without a single viewing never change. `datesDerived` in the answer says whether the season's dates come from its episodes (some watched episode has a dated viewing), so a client can show them read-only. The answer is the `GET` answer plus `tracking: { status, startedAt, finishedAt, rewatches, wantsRewatch }` of the season after the change. Like every write it bumps the user's content version. When a series follows an episode group, switching it recomputes the acting user's season entries from their watches once the new catalogs are fetched (a completed season that records none of its episodes is left as it is).
- `GET /api/series/{id}/filler?slug=` (the user's series, 404 otherwise): the series' episodes classified by AnimeFillerList for the "Skip the filler" preview, `{ slug, sourceUrl, counts, episodes: [{ seasonId, seasonNumber, key, number, title, absoluteNumber, category, watched, skipped }] }`, with `category` one of `filler`, `mixed`, `mangaCanon` and `animeCanon`. It reads the site on every call. A successful match also stores the category of every episode and the slug in the shared catalog (`season_filler`, one row per season), replacing what the series had, unless the request signed in with a read-only token; errors store nothing. The stored categories are what `filler` in the season episodes answer shows. Applying it is a `skip` per season with the `PATCH` above. See [skip-filler.md](skip-filler.md) for the pairing rules and the error codes.
- `PUT /api/seasons/{id}/rewatch-intent` (write scope) with `{ "wanted": true | false }`: sets or clears the user's intention to watch the season again, records no date and no viewing, and answers like the `PATCH` above.
- `GET /api/season-cache` (read scope is enough) lists the user's season entries whose stored status, dates, rewatches or counters differ from what their episodes say (`{ repaired: false, seriesChecked, drifts: [{ seriesId, seasonId, fields, stored, computed }] }`) and changes nothing; `POST /api/season-cache/repair` (write scope) rewrites those entries from their episodes and answers the same list with `repaired: true`. Seasons without a complete catalog, or completed with none of their episodes recorded, are never listed. The same check runs from the command line (`metrack season-cache [--repair] [--user <id>]`, over the home database) and as a scheduled job that only reports.
- `GET /api/next` (read scope is enough): the episode that is next for each series of the user, `{ rows: NextEpisodeRow[] }`, for the Next tab. A series has a row when it has a season in progress, a season with an open rewatch or one the user wants to watch again, a completed last started season followed by a season that is not completed or dropped, or when the whole series is completed and its rewatch has closed on a season that is not the last (the next season continues it); paused and dropped series have none, and season 0 is only chosen while it is the one in progress. The season is the lowest one with an open rewatch or that is completed and wanted again (its pass then counts from today), else the first in progress, else the one after the last completed season, else the one after the closed rewatch; the episode is the first aired, not skipped one not done in the current pass (`isDone`), as in the season page. A row carries `series` (id, title, cover, banner), `season` (id, number, title, cover, episodeCount), `episode` (number, key, title, stillPath, runtime, airDate, filler), `source` (`numbers` when the season has no stored complete catalog: the episode is then number `watchedCount + 1` with a null `key`), `availability` (`ready`, `airs` for an episode not aired yet, `premieres` for a season with nothing aired, with `airsOn`), `labels` (`rewatch`, `newSeason`), `progress` (the numbers the season progress bar takes) and `lastActivityAt`. Nothing is requested from TMDB or any provider: only the user's season entries are read for every series, then, for the series that have a row, their watches, the stored catalog of the picked season and its filler classification. Rows are sorted by `lastActivityAt` descending, the ones without it after, by the date of their latest viewing. `series=<id>` returns only that series' row, or an empty list when it has none. `series_episode_entry.last_activity_at` is the server time of the last change to the watched or skipped episodes of a series, written by the web app, tokens, the Jellyfin sync and the connector.
- `PUT /api/series/{id}/next-hidden` and `DELETE /api/series/{id}/next-hidden` (write scope, 204): take the series off the `GET /api/next` list and put it back. `PUT` stores `series_entry.next_hidden_at` with the server time; the series stays off the list while `next_hidden_at` is not older than the series' `last_activity_at` (a series without one counts as older), so marking or skipping any episode of it, from the web app, a token or the Jellyfin sync, brings it back by itself. Neither changes the status of a season. 404 when the series is not in the user's library.

## Metadata refresh

`POST /api/metadata/{type}/{id}/refresh` (`type` is a `MediaType`) asks the provider again, ignoring expiry, and answers a `RefreshResult`: `fresh`, `unchanged`, `updated` with the changed `fields`, or `failed` with the provider `error` (stored data is kept). Hand-edited fields are never overwritten. Types without a configured source (today everything except `movie` and `series`, or all of them without `TMDB_API_KEY`) answer 501 `no_metadata_source`.

## Search and adding titles

- `GET /api/search?type=&q=&year=`: `type` is one of `SEARCHABLE_TYPES` (`movie`, `series`, `videogame`, `book`), `q` is required and `year` is optional. Answers `{ "results": SearchResult[] }`. `externalId` is what to send to add the title, `existingId` is the id of the entity that already holds it (or null) so the UI can link instead of adding twice.
- `POST /api/titles` with `{ "type", "externalId" }` (`AddTitleRequest`): creates the entity from the provider, fills its metadata and downloads its images. A series also gets one planned season per TMDB season, skipping specials. Answers 201 with `EntityRef` (`{ type, id }`). A title that is already there answers 409 `already_added` with `details.existingId`.

Movies and series come from TMDB (needs `TMDB_API_KEY`) and games from IGDB (needs `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET`). A game is added once with its IGDB metadata (games have no metadata refresh) and its artwork: the official Steam library cover and hero when IGDB links the game to Steam, otherwise the IGDB cover and first screenshot. With `STEAMGRIDDB_TOKEN` set, a game on Steam is also linked to its SteamGridDB id, so the artwork picker offers community art for it. Books come from Open Library, which needs no key: the external id is the work id (`OL8479867W`), search results list the authors as their `overview`, and a book is added once with the title, cover, publisher and ISBN of the edition in `OPENLIBRARY_LANGUAGE` when there is one, and the authors, page count, first publish date, description and subjects of the work. A type whose provider is not configured answers 501 `provider_not_configured`. Games and books can still be created by hand with `POST /api/games` and `POST /api/books`.

## Unlinked inbox

Titles that arrived without an external id wait here (`UnlinkedTitle`).

- `GET /api/unlinked`: the list.
- `DELETE /api/unlinked/{id}`: dismisses one (204 or 404).
- `POST /api/unlinked/{id}/resolve` with `{ "ids": ExternalIds }` (`ResolveUnlinkedRequest`): creates the real entity and removes the title from the inbox. Answers 201 with `ResolveUnlinkedResponse` (`{ type, id, refresh }`). The ids that apply are: movies `tmdbId` and `jellyfinId`; series `tmdbId`, `tvdbId` and `jellyfinId`; games `igdbId`, `steamAppId` and `steamGridDbId`; books `openLibraryId` and `isbn`. At least one is needed (`ids_required`) and others are refused (`invalid_ids`). With a `tmdbId` for a movie or series and TMDB configured, the entity is added through the provider, exactly like `POST /api/titles`. Otherwise it is created from the inbox title and the given ids, and refreshed when a source exists. A season cannot be resolved by id (`cannot_resolve`): link its series instead. If creation fails (for example the id is already used, 409) the title stays in the inbox.

## Images

Kinds are `cover` and `banner` (`IMAGE_KINDS`); books only have `cover`.

- `GET /api/{collection}/{id}/images/{kind}`: candidates as `ImageCandidateList`: `{ candidates: ImageCandidate[], failures: [{ provider, error }] }`. A provider that fails is reported in `failures` and does not hide the others. TMDB covers movies, series and seasons (season posters only, no banners); SteamGridDB covers games that have `steamGridDbId` and needs `STEAMGRIDDB_TOKEN`. An entity without the needed id simply has no candidates.
- `PUT /api/{collection}/{id}/images/{kind}` with `{ "url" }` (`ImageChoice`): a candidate `url`, or any URL of a provider that offers that kind for that type. TMDB, Steam and IGDB images are linked: the field keeps the provider URL and the store keeps a copy as an archive, downloaded at the largest size the app displays (TMDB `w780` for covers and `w1280` for banners, IGDB `t_720p` and `t_1080p`; Steam as is) and recorded under the linked URL. Other providers (SteamGridDB, Open Library) are copied into the store as WebP. Owner and trusted users (`canUseOwnArtwork`) may also send a URL of any public site, copied as WebP and counted as their own, or the `/api/images/<hash>` of an image they uploaded (anything else is 400 `image_not_found`). For normal users anything that is not a provider URL is 403 `trusted_only`. URLs of any site must be `http` or `https` and resolve to public addresses, every redirect included, otherwise 400 `url_not_allowed`. Choosing marks the field as hand-edited and answers the detail. Covers and banners of your own that existed before stay.
- `DELETE /api/{collection}/{id}/images/{kind}`: clears the field, marks it as hand-edited and deletes the stored file (a copy or a linked image's archive) when nothing else uses it. Answers the detail.
- `thumbUrl` of a candidate is only for previews in the picker and is never stored.
- `POST /api/images` with the image file as the body (`Content-Type: image/*` or `application/octet-stream`): for the owner and trusted users (normal users get 403 `trusted_only`), also for images inside reviews. The server re-encodes it to WebP (applying the EXIF orientation and dropping EXIF, GPS, XMP and ICC data), scales it down to `IMAGE_MAX_DIMENSION` (default 1920 px) and counts it for the uploader's quota (the owner has none). Answers 201 with `UploadedImage` (`{ ref, mimeType, width, height, byteSize, usage }`; `usage` is `{ usedBytes, quotaBytes, imageEncoding, maxDimension }`, with `maxDimension` the configured `IMAGE_MAX_DIMENSION` the web recodes to, where `imageEncoding` is `server`, or `client` when the instance runs with `IMAGE_ENCODED_BY=client`: the web then recodes to WebP before uploading and the server rejects anything that is not WebP within the limits with 400 `unsupported_image` or 413 `image_too_large`); embed it in a review as `![alt](ref)`. Refusals: 400 `unsupported_image`, 413 `body_too_large` over `IMAGE_UPLOAD_MAX_MB` (default 5), 409 `image_quota_exceeded` over `IMAGE_QUOTA_MB`. Uploading bytes someone already owns adds you as an owner and counts for you too; bytes that match a provider image count for nobody.
- `GET /api/images/usage`: `ImageUsage` (`{ usedBytes, quotaBytes }`) of the signed-in user; `quotaBytes` is `null` for the owner, who has no limit. Provider images never count; own images (uploads and covers of your own from any site) do.
- `GET /api/images/{hash}` serves a stored image with long-lived private caching. Provider images and images a shared catalog row shows are for every user; an own image only for its owners and the instance owner, everyone else gets 404. `DELETE /api/images/{hash}` deletes it and clears every reference, and `POST /api/images/cleanup` deletes the images nothing uses (no cover or banner points at them, by reference or by the linked URL they archive, and no review embeds them) and that were stored or claimed more than 24 hours ago, and answers `{ "removed": [hash] }`. Deleting a user drops their ownership, so a cleanup afterwards frees only the images nobody else uses.

## Health

- `GET /api/health`: `HealthReport`. Answers 200 when `status` is `ok` and 503 with the same body when it is `degraded`, so the container health check fails. `features` lists optional capabilities of this deployment (`backups`: the `/api/backups` routes exist); the web hides the matching UI when a flag is false.

## Backups

- `GET /api/backups`: the stored backups, newest first, as `{ name, createdAt, sizeBytes, hasImages }[]`.
- `POST /api/backups`: takes a backup now, prunes to the retention count and answers 201 with the new backup. A failure answers 500 `backup_failed` with a generic message; the details are only in the server log.

## Home connector

The routes the home connector syncs through (see [connector.md](connector.md)). Only API tokens reach them (a browser session answers 403 `token_required`). A `connector` token acts on every user with a Jellyfin account in their settings; a personal `write` token only on its own user (403 `connector_other_user` for another one), and a `read` token cannot post. A user with no Jellyfin account set answers 404.

- `GET /api/connector/users`: the users the token may act on, `[{ id, name, jellyfinUser }]`.
- `GET /api/connector/users/{id}/sync-state`: `{ contentVersion, state }`, where `state` is the `SyncState` (movies, series, seasons, unlinked and, from the episode-tracking release on, `watches`: the user's watched episodes of each series that has any, `[{ seriesId, watched }]`) and `contentVersion` the user's content version at that moment.
- `POST /api/connector/users/{id}/sync` with `{ contentVersion, plan }` (`ConnectorSyncRequest`): 409 `content_changed` when the content version moved since it was read; 400 `plan_foreign_id` when the plan names a movie, series or season that is not the user's; otherwise it writes the plan with the same applier as `POST /api/sync/apply` (tracking fields and external ids only, never notes, reviews, ratings or images), bumps the user's content version and answers `{ result: SyncApplyResult, created: EntityRef[] }`. On the home server the writes share one SQLite transaction. On D1, which has no interactive transactions, they run one after another, so a failure halfway leaves what was written and the next plan, computed from the new state, finishes the job. A series change may carry `watches` (the series' merged watched episodes, keyed by TMDB episode id or `s<season>e<episode>`) and each season change `watchedEpisodes` and a nullable `jellyfinSeasonId`; all are optional, so a connector that predates them keeps working.
- `POST /api/connector/users/{id}/refresh/{type}/{titleId}` (`type` is `movie` or `series`): fetches the provider metadata of one title, 501 `no_metadata_source` when none is configured.

The release alert routes below follow the same rules, except that the users they accept are the ones with an ntfy topic in their settings (404 for the others).

- `GET /api/connector/alert-users`: the users the token may act on that have an ntfy topic, `[{ id, name }]`.
- `GET /api/connector/users/{id}/release-state`: `{ ntfyTopic, series, movies, alerts }` in one response: the followed series and movies that have a TMDB id as `[{ id, tmdbId, title }]`, and the keys `[{ subjectType, subjectId, kind }]` of the alerts already recorded.
- `POST /api/connector/users/{id}/seasons` with `{ seriesId, release, today }`: runs the season reconciliation of the release alerts with `release` (what TMDB announces for the series, fetched by the caller: `posterUrl`, `numberOfSeasons`, `seasons`, `nextEpisode`, `flatrateEs`) and the local date `today`, creating the announced seasons that are new, and answers `{ seasons: [{ season, airDate, created }] }` with the linked seasons and their ids. 404 when the series is not the user's.
- `POST /api/connector/users/{id}/release-alerts` with `{ alerts: [{ subjectType, subjectId, kind, title, message, sentAt }] }`: records alerts the connector delivered, once per (subject, kind), and answers `{ recorded }` with how many were new.

## Steam import

See [steam-import.md](steam-import.md). The routes answer 501 `steam_not_configured` when the server has no `STEAM_API_KEY` or no IGDB credentials, and `report` and `apply` answer 400 `steam_id_missing` when the user has not linked a Steam account.

- `GET /api/steam/report`: the `SteamImportReport`: `steamId`, `owned` (games on the account), `rows`, `upToDate` (games in the library whose stored time is already at least Steam's) and `unmatched` (games IGDB does not know by their Steam app id, listed and not importable). Each `SteamImportRow` has `appId`, `name`, `playtimeMinutes`, `recentMinutes`, `lastPlayedAt`, `action` (`update` raises the time of a game already in the library, `import` adds a game), `source` (`library`, `catalog` or `igdb`), `storedMinutes`, the proposed `status` (`in_progress` with time in the last two weeks, `paused` for other played games, `planned` for never played ones; `null` for an update) and `selected` (false for never played games). Reads Steam, IGDB and the database; writes nothing. 422 `steam_profile_private` when Steam returns no games (the profile or its Game details are private, or the account owns none), 502 `steam_key_rejected` or `steam_unavailable`.
- `POST /api/steam/artwork` (no body): prepares the artwork of the games the Steam import added with it deferred (archives their cover and banner, links SteamGridDB, falls back to IGDB art when Steam has none), as many as fit in one request, only among games in the caller's library. Answers `SteamArtworkResponse`: `{ processed, remaining }`; call it again while `remaining` is above 0.
- `POST /api/steam/achievements` (body `{ gameId?, asOf? }`, both optional): asks Steam for the achievements of the signed-in user's games that have a Steam app id (`ISteamUserStats/GetPlayerAchievements`, one request per game, using the SteamID64 in the user's settings) and stores them on the user's library entry: `achievementsUnlocked`, `achievementsTotal`, `achievementsLastUnlockedAt` (`YYYY-MM-DD`, UTC) and `achievementsCheckedAt` of the game. With `gameId` it checks that game only (404 when it is not in the library or has no Steam app id). Without it, it checks the next games of a pass, as many as fit in one Worker request (11), games with playtime first, then the least recently checked, and answers `{ processed, failed, remaining, asOf }`: send the returned `asOf` back until `remaining` is 0; the first request has no `asOf` and the pass is the games not checked since it. `failed` counts the games Steam could not answer (private game details, a Steam error); their counts are left as they were and they are still stamped with `achievementsCheckedAt`, so a pass always ends. `achievementsTotal` is `null` while unknown (never fetched, or every fetch failed), `0` when Steam says the game has no achievements and the number of achievements otherwise; never treat `null` or a total of 0 as complete. 400 `steam_id_missing` without a linked account, 501 without `STEAM_API_KEY`. See [steam-import.md](steam-import.md).
- `POST /api/steam/apply` (`{ "appIds": ["220", ...] }`, 1 to 10 numeric ids): recomputes the report from Steam's current answer for those ids and writes them; only the ids come from the client. Answers `{ outcomes: [{ appId, result, error? }] }` with `result` one of `updated`, `imported`, `skipped` (not owned, unmatched, already in the library, or Steam's time not greater than the stored one), `failed` or `deferred`. New games are added with their artwork linked and archived later (see the artwork route below). A request that would pass its subrequest budget leaves the last games `deferred` and untouched: send them again. Repeating a request adds nothing. 400 `invalid_batch` for an empty or longer list.

## Jellyfin sync

- `GET /api/sync/report`: the `SyncPlan` a sync would apply: `movies` (`MovieChange`), `series` (`SeriesChange` with its `seasons`), `unlinked`, `warnings`, `ignoredPlays` and `unmatchedTitles`. Reads Jellyfin and Jellystat and the database; writes nothing.
- `POST /api/sync/apply` with `{ "confirm": true }`: recomputes the plan on the server (a client-supplied plan is never trusted), writes it in one transaction and answers `{ plan, result: SyncApplyResult }`. A body without `confirm: true` is a 400.
- On the Cloudflare Worker none of these three exist: nothing there can read Jellyfin, and the home connector syncs through `/api/connector`.
- `POST /api/sync/webhook`: the target of the Jellyfin Webhook plugin. The body is ignored. Queues a sync for every user with a Jellyfin account after `SYNC_WEBHOOK_DELAY_SECONDS` of quiet and answers 202 `{ status: "queued", users }` (how many were queued); 501 when sync is not configured. When `SYNC_WEBHOOK_SECRET` is set, the request must carry it in the `X-Webhook-Secret` header or the `token` query parameter, or it answers 401 `bad_webhook_secret`.
- Report and apply act on the signed-in user with the Jellyfin account in their settings. Both answer 501 `sync_not_configured` unless the Jellyfin and Jellystat variables are set (see [jellyfin-sync.md](jellyfin-sync.md)) and the user has a Jellyfin account set.

## Release alerts

- `GET /api/watchlist`: the followed movies and series as `WatchlistEntry[]`, ordered by title. Each entry has `type`, `id`, `title`, `cover` and `banner` (image refs or null), `releaseDate` (a series shows the first air date of its newest season) and `nextEpisode`: `{ seasonNumber, episodeNumber, airDate, name }` (`name` may be null) for a series whose last release check announced a dated next episode, otherwise null, and always null for a movie. `seasonNumber` is the local season number when the check linked the provider season to one. The value is stored by the release check, never fetched when the list is read, so it only refreshes for users whose release alerts are checked and is null until the first check after an update.
- `PUT /api/watchlist/{movies|series}/{id}` and `DELETE /api/watchlist/{movies|series}/{id}`: follow and unfollow (the `follow` field, so a `PATCH` does the same). 204, or 404 for an unknown id.
- `GET /api/alerts?limit=100`: the alerts already sent as `ReleaseAlert[]`, newest first (`limit` from 1 to 500).

## Account

- `GET /api/account/export/data`: the signed-in user's data as JSON (`AccountExport`), the content of `data.json`: `format`, `exportedAt`, `user`, `settings` (without `ntfyTopic`), `publicPage`, `tokens` (`ApiToken[]`, no secrets or hashes), `invites` (the owner's invitations with who used them, never their codes; empty for everyone else), the merged `movies`, `series`, `seasons`, `videogames`, `books`, `episodeWatches` (per series the user has a per-episode record for: `seriesId` and `watched`, the episode keys with their viewings), `unlinkedTitles`, `releaseAlerts` and `images` (hash, ref, size and the archive path `images/<hash>.<ext>` in `file`). The web app calls it, fetches each file with `GET /api/images/{hash}` and builds the ZIP in the browser (`data.json` plus `images/`, named `metrack-export-user-<id>-<date>.zip`); an image it cannot fetch gets `file: null`. The home server sets `file` to null for an image whose bytes are missing; the Worker does not check the store, so there `file` is set for every image row. A token may call it.
- `GET /api/account/export` (home server only; the Worker answers 404): the same export as a ready-made ZIP (`application/zip`, `Content-Disposition: attachment`), built in memory on the server, for the CLI and other programs. A token may call it.
- `GET /api/account` (browser session only): `AccountStatus`, `{ deletion: { requestedAt, deleteAt } | null, canDelete, needsWelcome }`; `canDelete` is false for the owner and `needsWelcome` is true until a user who joined by invitation confirms their name and handle.
- `POST /api/account/deletion` (browser session only; `DeleteAccountRequest`: `{ confirm }`): schedules the deletion 7 days after the first request (asking again keeps the original date) and answers the `AccountDeletion`. `confirm` must be the user's handle (any case) or `delete`, otherwise 400 `confirmation_mismatch`; 403 `owner_cannot_delete` for user 1; a token gets 403 `session_required`.
- `DELETE /api/account/deletion` (browser session only): cancels a waiting deletion and answers the `AccountStatus`.
- `GET /api/catalog/unreferenced` (owner or trusted): `UnreferencedCatalogItem[]`, the items added by hand that no user has an entry for, all of them for the owner and only one's own for a trusted user.
- `DELETE /api/catalog/{movies|series|games|books}/{id}` (owner, or the trusted user who owns the item): deletes one of those items, 204; 404 when there is no such hand-added item (or it is someone else's), 409 `catalog_in_use` while any user has an entry for it.

The privacy page, `GET /privacy`, is outside `/api` and needs no sign-in. The erasure itself is not an endpoint: the server job does it once the 7 days have passed, and the owner schedules or cancels another user's deletion with `metrack users delete <id> [--cancel]`.

## Settings

- `PUT /api/users/{id}/role` (owner only, `RoleChange`: `{ "role": "trusted" | "normal" }`): answers the updated `User`; 400 `owner_role_fixed` for user 1, 404 for an unknown user. Takes effect on the user's next request.
- `GET /api/settings` (browser session only): `OwnSettings`, the signed-in user's `settings` (`UserSettings`: what their sync, alerts and vault mirror act on, plus their interface `language`, `null` when unset) their `publicPage` (`PublicPage`: `{ handle, enabled }`), whether they are the `owner` and `ntfyTopicGenerated`, true only on the Worker, where the server makes the ntfy topic (see the next two routes).
- `PATCH /api/settings` (browser session only; `{ "language"?: "es" | "en" | null, "steamId"?: string | null }`, at least one): sets the signed-in user's interface language and, with `steamId`, their Steam account, given as a SteamID64, a `steamcommunity.com/profiles/<id>` or `/id/<name>` address or a bare vanity name; a name is resolved through Steam and the SteamID64 is stored, `null` or an empty text unlinks it (400 `invalid_steam_profile`, 400 `steam_profile_not_found`, 501 `steam_not_configured` for a name without a key). For the language, `null` follows the browser (the web app falls back to Spanish when the browser offers neither). Answers the stored `UserSettings`; 400 for any other value or field. The owner cannot set it for others through `PATCH /api/users/{id}/settings`.
- `POST /api/settings/ntfy-topic` (browser session only; Worker only, absent at home): turns the signed-in user's release alerts on or regenerates their topic. The server makes a new random topic, `metrack-` plus 160 random bits in 32 lowercase base32 characters (`[a-z2-7]`, 40 characters in all), stores it and answers the stored `UserSettings`; the previous topic is simply no longer used. The user subscribes to `https://ntfy.sh/<topic>`. The Worker only stores the topic and sends nothing: alerts are sent from the home connector.
- `DELETE /api/settings/ntfy-topic` (browser session only; Worker only): turns the signed-in user's release alerts off by clearing the topic. Answers the stored `UserSettings`.
- `PATCH /api/settings/public-page` (browser session only; `PublicPagePatch`: `{ handle?, enabled?, avatar?, intro?, description?, about?, giscus? }`): sets the signed-in user's own handle, switch and profile. `avatar` is a stored image reference (`/api/images/<hash>`) the user can read, normally one just uploaded with `POST /api/images`, or `null`; `intro` (100 characters), `description` (1000) and `about` (Markdown, 20000) are trimmed and an empty string or `null` clears them; `giscus` is `{ repo (owner/name), repoId, category, categoryId }` (all four required, 100 characters each) or `null`, and comments appear on item pages only while it is set. Omitted fields keep their value. The handle is trimmed and lowercased, `null` or an empty string clears it. Answers the stored `PublicPage`; 400 `invalid_handle` (3 to 30 characters of `a-z`, `0-9` and `-`, not a reserved word), 400 `handle_required` when the result would be a page that is on without a handle, 400 `invalid_avatar`, `invalid_public_page` (a text too long) or `invalid_giscus`, 409 `handle_taken`. The pages themselves are served outside `/api`, with no sign-in, under `/u/<handle>/` (see [jellyfin-sync.md](jellyfin-sync.md)).
- `GET /api/users` (owner only): `UserWithSettings[]`, every user with their settings, by id.
- `GET /api/users/summary` (owner only): `UserSummary[]`, every account by id with `{ id, name, email, role, createdAt, usedBytes, deletion }`: the email, the sign-up date, the bytes of images they own (the quota usage) and their waiting deletion, if any.
- `POST /api/users/{id}/deletion` (owner only): schedules the deletion of an account like the account's own request (the 7-day grace period, never immediate) and tells the user through their ntfy topic; answers the `AccountDeletion`. 403 `owner_cannot_delete` for user 1, 404 for an unknown user. `DELETE /api/users/{id}/deletion` cancels it, 204.
- `PATCH /api/users/{id}/settings` (owner only): changes some of `jellyfinUser`, `ntfyTopic` and `mirrorLinkPrefix` (on the Worker `ntfyTopic` is refused with 400, since the topic is generated by `POST /api/settings/ntfy-topic`); a string is trimmed, `null` or an empty string clears the setting. Answers the stored `UserSettings`; 400 `invalid_settings` with the problem of each invalid value in `details`, 400 for any other field (the vault folder `mirrorDir` is only set from the command line), 403 for anyone but the owner, 404 for an unknown user.
